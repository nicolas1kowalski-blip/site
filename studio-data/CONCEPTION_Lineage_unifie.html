3. Maîtrise & écriture (le cas « deux applis modifient le même attribut »)

Principe : un attribut = un maître pour une ligne donnée. « Deux applis écrivent le même attribut » se résout ainsi :

Situation sur l'attributModélisationSanté / signal
1 seul « écrit »maître uniqueréférence de la réconciliation
≥2 « écrit », conditions disjointes (ex. type=ASSURANCE / type=MAINTENANCE)maîtrise contextuelle (déjà dans l'app) : 1 maître par lignepas de conflit
≥2 « écrit », chevauchement / sans conditionautorisé, mais ALERTE « conflit de maîtrise » ; arbitrage optionnel (priorité / dernière écriture / par champ)divergence entre écrivains mesurée (« les 2 maîtres divergent sur X % »)
Comportement par défaut retenu : on ne bloque pas la déclaration d'un 2ᵉ écrivain ; on lève une alerte de conflit et on propose de la lever soit par une condition (partage de périmètre), soit par une règle d'arbitrage. Le conflit devient un indicateur de santé, pas un blocage.

4. Dérivation depuis les données (bouton « Synchroniser »)

La carte se reconstruit à partir de ce que l'app connaît déjà :

Source de véritéCe qui est dérivé
Tables conçues (design.sources, SOURCE_ORIGINE)arêtes source → table conçue (« alimente » ; ≥2 sources ⇒ badge consolidation)
Relations du modèle (MCD) / clés étrangères(option) arêtes table ↔ table
Applications & processus (usage : tables, colonnes, objets)liens « lit » application → table/attribut
Objets métier + rôles des sourcesalimente la vue objet et les liens « écrit » (maître/contributeur) + maîtrise contextuelle
Champ origine des tablesétiquette « alimentée par <système> » (regroupement visuel, pas un nœud)

À chaque synchro : le dérivé est recalculé ; les réglages manuels (points de mesure, clés, attributs contrôlés, SLA, transformations, arbitrages, flux ajoutés) sont préservés (ré‑appariés par identité).

5. Ce qu'on mesure

  • Fraîcheur : sur une table (retard vs fréquence du dictionnaire). Une application hérite de la fraîcheur des tables qu'elle lit.
  • Distorsion (réconciliation) : uniquement sur les arêtes « alimente » table → table dont les deux bouts sont des tables réelles, clé par clé et attribut par attribut (déjà en place en v5.2).
  • Conflit de maîtrise : divergence entre deux écrivains d'un même attribut (nouveau, §3).
  • Impact : si une table change, quelles applications (via « lit ») et quelles tables aval sont touchées.

6. Migration de l'existant (sans perte)

  • Nœuds actuels (avec tableName) → deviennent des nœuds table ; l'ancien champ « rôle » saisi devient un simple point de départ, désormais déduit.
  • Arêtes actuelles (clé par côté, attrPairs, SLA, transformation, lastRun) → conservées en tant qu'arêtes « alimente » manuelles.
  • Le champ flow évolue de façon rétro‑compatible (comme on l'a fait pour attrPairs).
  • 1ʳᵉ « Synchronisation » : le dérivé complète (n'écrase pas) ; doublons fusionnés par identité.
