🧭 Conception — « Lineage & santé » unifié

Proposition de remaniement pour lever les incohérences : dériver le graphe de la gouvernance existante plutôt que le re-saisir, et distinguer clairement système, jeu de données et objet métier. Document de cadrage — à valider avant tout développement.

1. Le constat

Trois défauts de conception, identifiés à juste titre :

  1. Deux lineages qui s'ignorent. L'onglet « Lineage » (dérivé : attributs, objets, usage) et le nouvel écran « Lineage & santé » (saisi à la main) coexistent sans se parler.
  2. Re-saisie inutile. L'app connaît déjà les flux (rôles des sources d'un objet, usage des applications, consolidation des tables conçues, relations du modèle) — les redéclarer manuellement est redondant et source d'erreurs.
  3. Confusion système / source / objet. Un « nœud » = un système avec une source chargée collée dessus, ce qui laisse croire que le nœud est la source. Or la source chargée n'est qu'un point de mesure ; la vraie origine d'un flux est le système amont, et un objet alimenté est une cible, pas une source.

2. Principes directeurs

  • La carte se dérive, elle ne se saisit pas. Le graphe est reconstruit depuis la gouvernance ; le manuel ne sert qu'aux ajustements et aux flux non déclarés.
  • Identité ≠ mesure. Un nœud a une nature et une identité (issue d'un objet, d'une application, d'une table…). La source chargée est un point de mesure qu'on rattache à un nœud pour calculer fraîcheur et distorsion — jamais l'identité du nœud.
  • Le manuel survit à la resynchronisation. Les ajustements humains (points de mesure, clés, attributs contrôlés, SLA, transformations, flux ajoutés) sont préservés quand on régénère la carte.
  • 100 % local, sans perte. Aucune régression ; migration transparente de l'existant.

Clé de voûte : une arête dérivée décrit le flux (structure) ; ses réglages de santé (clé, attributs, SLA…) sont une surcouche manuelle rattachée par identité (source, target). Ainsi « Synchroniser » recalcule la structure sans effacer les réglages de contrôle.

4. Dérivation depuis la gouvernance

Un moteur « Synchroniser depuis la gouvernance » (re)construit nœuds & arêtes dérivés à partir de :

Source de véritéNœuds créésArêtes créées
Objets métier + rôles des sourcesl'objet (objet) ; chaque source (jeu de données)maître → objet (consolide) · contributeur → objet (alimente) · objet → destinataire (lit)
Tables conçues (design.sources, SOURCE_ORIGINE)la table conçue (consolidée) ; ses sourceschaque source → table conçue (consolide)
Applications & processus (usage : tables, colonnes, objets)l'application (application)table/objet → application (lit)
Relations du modèle (MCD), clés étrangères—(option) table ↔ table (lit / jointure)

À chaque synchro : les arêtes/nœuds origin:'derived' sont remplacés ; les origin:'manual' et tous les réglages de santé rattachés sont conservés (ré-appariés par identité). Rien de ce que tu as réglé à la main n'est perdu.

Exemple dérivé automatiquement : ctC360.csv ──consolide──▶ ⟦ Contrat ⟧ ──lit──▶ BI Ventes AVENANT.csv ─alimente──▶ (objet) ──lit──▶ Facturation ADRESSE.csv ─alimente──▶ ──lit──▶ Data Lake (les « points de mesure » = les .csv chargés ; la fraîcheur/distorsion se calcule là où deux jeux de données réels encadrent une arête)

5. Couche santé (mesure)

  • Fraîcheur : rattachée à un nœud portant un point de mesure (jeu de données chargé) → retard vs fréquence attendue du dictionnaire (SLA). Rien de neuf, mais clairement « au niveau du point de mesure ».
  • Réconciliation (distorsion) : sur une arête dont les deux extrémités ont un point de mesure — on compare le jeu de données amont (transformé par la règle rejouable) au jeu aval, clé par clé et attribut par attribut (déjà en place en v5.2).
  • Contrainte assumée : la carte est 100 % dérivable ; les contrôles exigent des données réelles chargées aux deux bouts. Là où il manque un point de mesure, on affiche « non mesurable » (mais le flux reste visible).

Deux options — à trancher (voir §9) :

B. Deux écrans, mais reliésOn garde « Lineage » et « Lineage & santé », mais ce dernier dérive désormais du même modèle (bouton Synchroniser).+ rapide, peu de risque · − deux entrées dans le menu

Dans les deux cas, l'écran propose : Synchroniser depuis la gouvernance, bascule Systèmes / Jeux de données / Objets (granularité), fiche nœud (nature, provenance, point de mesure, fraîcheur, impact), fiche arête (flux, transformation, santé attribut par attribut, export), et le bandeau de synthèse + journal déjà en place.

7. Migration de l'existant (sans perte)

  • Les nœuds actuels (avec tableName) → deviennent des nœuds jeu de données (ou système avec point de mesure), origin:'manual'.
  • Les arêtes actuelles (clé par côté, attrPairs, SLA, transformation, lastRun) → conservées telles quelles en origin:'manual'.
  • À la 1re « Synchronisation », les flux dérivés viennent compléter (pas écraser) ce qui existe ; les doublons évidents sont fusionnés par identité.
  • Le modèle state.governance.flow évolue de façon rétro-compatible (comme on l'a déjà fait pour attrPairs).
